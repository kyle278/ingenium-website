# Free call request journey

Applies the `form-experience` skill to `/book-a-call`. The outcome is an accepted request for a free 15-minute call. Ingenium then contacts the visitor on their supplied phone number to agree a time; this form does not reserve a calendar slot.

## Journey

1. **Your call:** choose an icon card to answer and continue. The five choices include help deciding. Valid service/package links reuse their known topic and open timing directly. Timing uses an optional date and native radio buttons, then explicit Continue; arrow keys never navigate.
2. **Your details:** separate First name and Last name fields plus a required phone number let Ingenium arrange the call. Email, business name and notes are optional behind a disclosure. A selected offer’s pricing is available in a separate optional disclosure. Continue validates contact details before consent.
3. **Privacy & send:** two clickable cards, backed by independent native checkboxes: required Privacy Policy acknowledgement and optional marketing consent. Both start unselected. Clicking a card toggles only its own value; it never advances or submits. The policy link opens independently. If email marketing is selected, a required email field appears for that opt-in and can reuse the optional contact address. Turning marketing off removes this requirement and excludes that marketing-only draft. Only the final button sends the request. There is no review page or repeated answer summary for this simple call request.

Named progress stages accommodate the shorter package route. In-form Back preserves independent answers and provides correction without a review screen. Switching to another service clears the package, including its price and submitted interest; choosing the website topic again preserves a compatible website package. Preselected mobile routes scroll directly to the timing panel without opening the keyboard. The single URL remains stable: browser Back leaves the page normally. Refreshing or leaving discards the in-memory draft; personal answers are not written to browser storage or URLs.

## Interaction and delivery

Only the active screen is mounted. A synchronous originating-step guard prevents repeated stale activations; double-click capture and held-key repeat protection cover rapid input. Focus moves to the new heading, the document title follows the question, and the form scrolls into view without opening the mobile keyboard. CSS provides 200ms transitions; reduced motion removes animation and travel. No artificial wait or animation event controls progression.

Submission keeps the existing `/api/enquiry` → Portal `contact` integration, `free-call` intent, Europe/Dublin timezone, consent evidence, attribution rules and request-ID convention. Final submission is guarded synchronously and disabled while pending. Errors retain all answers. Confirmation requires an accepted receipt from the existing transport; an uncertain response keeps the original request ID and existing advice to contact Ingenium before resending. No draft or step events create leads.

The separate manual visibility-check form retains its existing fields, consent and email-delivery requirement. The callback exception in `validateEnquiry` is limited to `contact` + `free-call`; other request types still require email. Source inspection of the existing legacy Portal submission handler confirms it stores scalar fields without requiring an email. Mocked API tests verify the website forwards real first/last name values and phone-only data without inventing an email. Live Portal receipt, CRM mapping and notifications remain unverified by these local tests.

## Verification

The production build, targeted ESLint check and all 77 automated tests pass. Component tests cover navigation, invalid attempts, Back corrections, package invalidation, consent, failures, native typing and duplicate submissions. Browser verification intercepts `/api/enquiry`; it exercises the actual UI without creating real Portal leads. Checks pass at 1440×1000, 390×844 and 375×667, including reduced motion, keyboard focus/arrow behaviour, native validation, callback phone requirement, phone-only success, separate-name mapping, conditional marketing email, card text/padding activation, independent selected states, keyboard toggling, privacy link opening without toggling acceptance, failed requests, pending duplicates, every package route and a visibility-form regression. At 200% text size, choices reflow and the form remains scrollable without horizontal overflow.

Topic, timing and contact steps fit the tested normal mobile viewports after their question comes into view. Consent cards, expanded optional details and enlarged text can require page scrolling to keep all consent wording readable; there is no clipping, fixed-height form or nested scroll region. Browser checks are recorded by `.codex-preview/verify-call-journey.cjs`. They do not prove delivery to the live Portal, emulate an actual soft keyboard or substitute for a manual screen-reader test.
